# 广播通知原子发布设计

## 目标

修复广播幂等记录先于通知 fan-out 单独提交所造成的“占位记录中毒”问题：当 fan-out 失败时，不得留下可被回放为成功的 `recipients=0` 记录；使用相同 `broadcast_id` 重试必须能够重新执行并成功发布。

## 方案

在模型层提供一个原子广播发布操作，并在同一个 SQLite 事务中完成：

1. 尝试插入 `broadcast_publications` 记录以 claim `broadcast_id`。
2. 如果 ID 已存在，读取并返回此前已经完成的发布结果，不再 fan-out。
3. 如果 claim 成功，批量插入所有用户的通知。
4. 将广播记录更新为最终标题、收件人数和邮件标志。
5. 提交事务。

任何步骤抛出异常时回滚整个事务。因此失败后既不会残留广播占位记录，也不会残留部分站内通知，相同 ID 的重试可以重新 claim。

SQLite 会串行化冲突写事务；并发的相同 ID 请求在首个事务提交后读取其完整结果，不会观察到半完成占位记录。

## 邮件边界

邮件保持 best-effort 行为，在站内通知事务成功提交后才启动后台线程。每位用户继续使用 `broadcast-{broadcast_id}-{user_id}` 作为 Resend 幂等键。本次不引入持久化邮件 outbox。

## API 行为

- 首次成功发布：返回 `ok`, `recipients`, `email`。
- 相同 `broadcast_id` 重放：返回首次完成结果并带 `replayed: true`。
- fan-out 或事务失败：请求失败且数据库整体回滚；相同 ID 后续可以重新发布。

2. 保留现有正常重放、变更 payload 重放和模型单次 claim 覆盖。
