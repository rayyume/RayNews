# 服务端 AI 告警防抖设计

## 目标

当服务端 AI 在短时间内反复失败、成功时，管理员不应收到连续的“失效 / 恢复”邮件。保留首次故障的及时告警，并仅在健康状态稳定后发送一次恢复通知。

## 现状与根因

当前逻辑在连续 `SYSTEM_AI_FAILURE_ALERT_THRESHOLD`（默认 3）次失败后发送一次故障通知，并以持久化标记保证持续故障不重复通知。任意一次成功调用会立即清除该标记并发送恢复通知；下一次达到失败阈值则视为新故障并再次通知。因此上游 API 抖动会不断创建新的故障事件，现有逻辑没有时间维度的通知限频。

## 已确认策略

1. 连续 3 次失败后，立即向管理员发送一封故障通知。
2. 一旦故障事件已经通知，后续失败不会重复通知；单次成功也不会立即恢复事件。
3. 只有连续 3 次真实的服务端 AI provider 调用成功，才关闭该事件并发送一封恢复通知。
4. 任一故障或恢复通知送达后，30 分钟内不发送新的服务端 AI 故障事件通知。冷却期内发生的故障会作为“已抑制事件”被记录为活跃状态，直到稳定恢复，但不会补发过期的故障或恢复邮件。
5. 管理员保存新的服务端 AI 配置时，清除当前事件与冷却状态，使新配置能被独立验证和告警。

## 架构与状态

保留现有 `app_state` 持久化，以支持多线程、重启和多进程。把 `system_ai_failure_alerted` 扩展为三态：`0`（无活跃事件）、`1`（活跃且已通知）、`2`（活跃但因冷却期抑制）。新增一个持久化的最近通知时间键。

`models.py` 将提供一个事务性声明函数：仅当没有活跃事件时，原子地检查最近通知时间、标记新事件为已通知或已抑制，并返回该调用者是否应发送邮件。单独的持久化函数会在至少一位管理员收到通知后更新时间；通知未送达时会释放事件，使下一次失败可重试。

`web_server.py` 的内存健康状态将增加连续成功计数。失败将其重置；成功将失败计数归零，并且只在存在活跃事件且连续成功达到阈值时关闭该事件。关闭时只有状态为 `1` 的事件发恢复通知；状态为 `2` 的事件静默关闭。

## 配置

- `SYSTEM_AI_RECOVERY_SUCCESS_THRESHOLD`：默认 `3`，必须至少为 `1`。
- `SYSTEM_AI_ALERT_COOLDOWN_SECONDS`：默认 `1800` 秒，必须至少为 `0`。

## 测试

在 `tests/test_system_ai_health_alert.py` 添加回归覆盖：

- 单次成功不会结束已通知的故障；第 3 次连续成功才发恢复通知。
- 恢复前再次失败会重置成功计数，并且不再发重复故障通知。
- 冷却期内的新事件不发送故障或恢复通知；冷却期后可重新发送。
- 冷却状态和最近通知时间跨进程状态存储工作；通知未送达仍可重试。
- 既有阈值、重启去重、配置重置和真实 provider 调用边界的测试继续通过。
