# 个人 AI 共享复核连续失败阈值设计

## 背景

当前开启“共享 AI 结果”的用户会在容器启动约 60 秒后接受第一次个人
AI API 后台复核，此后默认每小时复核一次。任何一次后台失败都会立即把
`share_suspended` 置为 `1`、停止共享并发送通知。服务商短时波动因此会造成
不必要的暂停/恢复通知。

用户主动触发的检测含义不同：保存或更换个人 API、点击“测试连接”、开启
“共享 AI 结果”时，用户正在要求系统确认当前配置。此类失败应继续立即生效。

## 目标

1. 定时后台复核只有在同一份个人 AI 配置连续失败两次后才暂停共享。
2. 第一次后台失败期间保持共享有效，不发送暂停通知。
3. 任意成功检测清零后台连续失败状态。
4. 保存/更换 API、手动测试、手动开启共享的失败仍立即暂停已有共享。
5. 连续失败状态跨容器重启保留，并且旧配置的延迟结果不能影响新配置。
6. 暂停和恢复边沿各只通知一次。

## 非目标

- 不改变默认每小时复核间隔及最短五分钟限制。
- 不增加可配置的失败阈值；阈值固定为两次。
- 不删除已经写入 `ai_results` 的历史共享缓存。
- 不改变服务端系统 AI 的独立健康告警阈值。
- 不把同一轮中的快速重试当作第二次后台复核。

## 方案选择

采用数据库持久化后台失败状态。内存计数会在容器重启时丢失，也无法安全扩展
到多个进程；同一轮立即重试则不符合“连续两个后台检测周期”的语义。

### 新增状态

在 `user_settings` 增加：

- `share_revalidation_failure_streak INTEGER NOT NULL DEFAULT 0`
- `share_revalidation_failure_revision INTEGER`
- `share_revalidation_last_failure_at TEXT`
- `share_revalidation_last_failure_error TEXT`

`failure_revision` 把计数绑定到 `ai_configs.revision`。检测结果的错误文本继续
经过 `_compact_share_error()`，数据库、接口和通知中都不得保存服务商原始响应、
密钥或令牌。

现有 `share_last_check_*` 字段仍代表决定当前共享访问资格的正式验证结果。
第一次容错失败不能覆盖最近一次成功验证，否则 `is_share_active()` 会立即变为
假；第一次失败改由上述独立字段记录。

## 状态转换

### 后台复核失败

对 `_run_ai_share_revalidation_once()` 中同一用户、同一配置版本的失败结果：

1. **连续失败 0 → 1**
   - 原子写入 streak、revision、失败时间和安全错误摘要。
   - 保持 `share_suspended=0`。
   - 不修改最近一次正式成功验证。
   - 不发送站内通知或邮件。
   - 返回状态 `pending_failure`。

2. **连续失败 1 → 2**
   - 在同一事务中把 streak 增至 2，并设置：
     - `share_suspended=1`
     - `share_last_check_ok=0`
     - `share_last_check_at=<本次时间>`
     - `share_last_check_error=<安全错误摘要>`
     - `share_last_check_revision=<当前配置版本>`
   - 提交后发送一次 `share_suspended` 站内通知，并尽力发送邮件。
   - 返回状态 `suspended`。

3. **已经暂停后的继续失败**
   - 可更新时间/安全错误摘要，但不产生新的状态边沿和通知。
   - 返回状态 `unchanged`。

若检测开始后用户关闭共享或 API 配置版本发生变化，结果返回 `not_opted_in`
或 `stale`，不得增加旧计数、暂停、恢复或通知。

### 后台复核成功

- 清零 streak，并清空 failure revision/time/error。
- 更新正式成功验证字段。
- 若用户已经暂停，解除暂停并发送一次 `share_restored` 通知。
- 若用户仍然正常共享，只更新健康状态，不发送通知。

### 用户主动检测

以下路径继续使用阈值 `1`：

- `POST /ai/test-connection`
- 已开启共享时保存或更换 `PUT /ai/config`
- `PUT /settings` 开启或重新确认共享

主动失败立即清空后台待确认状态并暂停已有共享，发送一次暂停通知。主动成功
清空后台待确认状态并按现有规则保持或恢复共享。

首次从关闭状态开启共享时，如果连接测试失败，共享保持关闭；因为不存在从
有效共享到暂停的状态边沿，不发送“共享已暂停”通知。

## 原子性与并发

`models.py` 提供一个专用于后台失败记录的事务函数。事务使用当前项目已有的
SQLite 写入序列化方式，并在写入条件中同时校验：

- `share_ai_results = 1`
- 当前 `share_suspended`
- `ai_configs.revision`
- 已记录的 failure revision/streak

只有取得 `0 → 1` 或 `1 → 2` 状态边沿的调用者能返回对应状态；只有取得
`1 → 2` 的调用者能发送暂停通知。并发的重复失败不能发送两条通知。

主动检测沿用 `_apply_share_connectivity_result()` 的配置版本 CAS，并在成功应用
当前版本结果时一并清空后台连续失败状态。

## 接口与界面

`GET /settings` 增加以下安全字段：

- `share_revalidation_failure_streak`
- `share_revalidation_last_failure_at`
- `share_revalidation_last_failure_error`

不向前端暴露 failure revision。

当共享仍有效且 streak 为 1 时，“用户设置 → 共享”显示黄色提示：

> ⚠️ 后台复核暂时失败（1/2），共享仍在运行；下次复核成功将自动清除，连续失败才会暂停。原因：…

暂停和正常成功状态继续使用现有文案。前端通知轮询仍只在收到
`share_suspended`/`share_restored` 时刷新共享状态，第一次后台失败不生成通知。

## 错误处理

- 连接超时、HTTP 错误、空响应和其他连接测试失败均算一次失败。
- 单个用户检测异常不得终止其余用户复核；保留现有循环级日志，并确保状态函数
  的数据库异常不会产生虚假的通知。
- 邮件发送继续是尽力而为；邮件失败不回滚已经提交的暂停状态和站内通知。
- 第一次失败的错误也必须清洗，不保存任意服务商响应正文。

## 测试与验收

自动化测试至少覆盖：

1. 第一次后台失败记录 `1/2`，`is_share_active()` 仍为真，无通知。
2. 同版本第二次后台失败暂停共享，并且站内通知/邮件各一次。
3. 两次失败之间一次后台成功清零计数，后续失败重新从 `1/2` 开始。
4. 手动测试、保存新配置和重新开启共享失败时立即暂停已有共享。
5. 主动成功清零后台失败状态；已暂停用户恢复且只通知一次。
6. 旧配置的失败不能累加到新配置。
7. 容器重启等价的模块状态重建后，数据库中的 `1/2` 仍能成为下一次失败的前置状态。
8. 两个并发第二次失败只产生一次暂停通知。
9. 关闭共享后到达的后台失败不改变状态。
10. 第一次失败的 `/settings` 响应和前端黄色提示不包含密钥或原始服务商正文。

验收时把后台复核函数替换为可控成功/失败响应，验证：

- 失败、失败：第一次继续共享，第二次暂停并通知。
- 失败、成功、失败：两次失败均只显示 `1/2`，共享始终有效。
- 第一次后台失败后重启进程，再失败：暂停并通知。
- 任一时点手动测试失败：无需等待第二次，立即暂停并通知。
