# 通知操作设计

## 目标

完善“我的通知”的操作能力：用户可以单条或批量标记已读、删除通知；删除操作只影响当前登录用户，并在慢网络下保持列表和未读角标一致。

## 范围

- 通知列表的单条“已读”和“删除”操作。
- 列表顶部的“全部已读”和“全部删除”操作。
- 通知详情底部的“已读”和“删除”操作。
- 用户范围内的删除与批量已读 API。
- 对应模型、路由和前端回归测试。

不包含回收站、撤销、跨用户管理或通知分页改造。

## 交互设计

### 列表

- 每条未读通知右侧依次显示“已读”“删除”；已读通知只显示“删除”。
- 删除按钮使用红色实底色，已读按钮沿用普通操作样式。
- 点击通知标题或其余行区域进入详情；操作按钮阻止冒泡。
- 列表顶部右上角显示“全部已读”和“全部删除”。
- “全部已读”直接执行，仅影响未读通知。
- “全部删除”先弹出浏览器确认框；确认后删除当前用户全部通知。

### 详情

- 未读通知在底部显示“已读”和红色“删除”。
- 已读通知只显示红色“删除”。
- 删除当前详情通知后返回列表；若列表为空，显示现有空状态。

### 反馈与状态

- 单条已读、单条删除与批量操作均采用乐观更新，避免等待网络请求才反馈。
- 删除请求失败时恢复被删除的本地条目和未读数量，并显示失败提示。
- 已读请求的既有并发保护保留。
- 刷新中的 GET 结果必须与待处理的删除/已读操作合并，不能重新显示待删除条目或还原待标记的未读状态。

## 后端 API

所有接口使用既有 `require_role("user", "admin")`，并以 `g.user_id` 限制数据范围：

- `POST /notifications/read-all`
  - 将当前用户所有未读通知标记为已读。
  - 返回 `{ok: true, unread: 0}`。
- `DELETE /notifications/<nid>`
  - 删除当前用户拥有的单条通知；不存在、已删除或属于其他用户时仍幂等返回成功。
  - 返回 `{ok: true, unread: <remaining>}`。
- `DELETE /notifications`
  - 删除当前用户所有通知，幂等。
  - 返回 `{ok: true, unread: 0}`。

模型层提供相应的用户限定函数，并提交事务。数据库表不需要迁移。

## 前端结构

- 在通知面板标题栏或列表内容顶部增加批量操作容器，复用通知按钮的紧凑尺寸。
- 新增危险操作 CSS 类，使用红色背景、白色文字，并提供悬停/禁用态。
- 维护待删除通知 ID 集合，类似现有待已读集合；刷新时过滤这些 ID。
- 批量删除期间使用一个批量待处理标记，刷新时不接受旧列表快照。
- 成功后进行一次权威刷新，失败时按操作前快照恢复。

## 测试与验收

### 模型与路由

- 单条删除只能删除本人通知，且更新未读计数。
- 全部已读只影响本人未读通知。
- 全部删除只影响本人通知，重复调用保持幂等。

### 前端

- 未读列表项的操作顺序为“已读”“删除”，没有“查看”按钮。
- 删除按钮带危险样式。
- 顶部批量操作、详情删除按钮均会渲染。
- 乐观删除立即移除列表项；失败时回滚。
- 删除中的通知不会被旧刷新响应重新插入。

### 手动/浏览器验证

- 单条删除、全部已读、全部删除（含确认）和详情删除均可操作。
- 慢请求期间，状态即时更新；关闭并重新打开通知面板后状态仍正确。
