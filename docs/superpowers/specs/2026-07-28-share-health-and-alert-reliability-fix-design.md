# 共享健康状态与管理员告警可靠性修复设计

**日期：** 2026-07-28
**目标分支：** `dev`

## 目标

修复两个审查问题，同时保持现有 API 响应和数据库结构兼容：

1. 已认证用户不能通过 `PUT /settings` 伪造共享 API 健康状态、解除服务端暂停或绕过个人 AI API 连通性校验。
2. 系统 AI 与每日摘要管理员告警在一次通知投递失败后不会被永久标记为已送达，后续失败调用可以重试。

## 非目标

- 不改变共享功能的用户意图字段或前端交互。
- 不改变系统 AI 连续失败阈值、每日摘要重试次数或邮件发送策略。
- 不新增数据库表或迁移。
- 不重构通用通知系统。

## 设计

### 1. 隔离客户端设置与服务端健康状态

`PUT /settings` 在处理请求后立即无条件移除以下服务端拥有的字段：

- `share_suspended`
- `share_last_check_at`
- `share_last_check_ok`
- `share_last_check_error`
- `share_last_check_revision`
- `share_current_config_revision`
- `share_intent_revision`
- `share_active`

该过滤不依赖请求中是否包含 `share_ai_results`。共享主开关和三个查看选项仍按现有逻辑保存；健康状态只能通过现有内部连通性转换函数更新。

为降低未来其他调用误用的风险，通用 `set_user_settings()` 和带版本 CAS 的设置函数不再接受共享健康字段。内部健康更新继续通过 `apply_share_connectivity_transition()` 完成；关闭共享时需要清除暂停状态的逻辑由一个明确的内部更新入口处理，而不是重新开放客户端可写白名单。

### 2. 让告警完成标志反映实际投递结果

`_notify_admins()` 返回成功写入站内通知的管理员数量。单个管理员的邮件仍是尽力而为；站内通知写入是判断告警是否已送达的最低可靠信号。

系统 AI 告警流程：

1. 保留当前持久化抢占，避免并发调用重复发送。
2. 执行管理员通知。
3. 若成功写入数量为零，则撤销持久化告警标志，并恢复内存中的可重试状态。
4. 下一次达到阈值后的失败调用重新尝试告警。

每日摘要告警流程采用相同语义：抢占后若没有任何管理员站内通知成功，则把该日期的 `alerted` 恢复为 `0`，允许下一次调度调用重试。成功送达至少一位管理员后保持现有去重行为。

为避免把“没有管理员账号”变成每分钟无意义重试，零管理员场景记录日志但仍视为没有可送达对象；由于以后可能创建管理员，状态保持可重试。

## 错误处理

- 撤销告警状态失败时记录错误，不遮蔽原始后台任务失败。
- 邮件失败但站内通知成功时，告警视为已送达，不重复创建站内通知。
- 部分管理员站内通知成功时，告警视为已送达，避免已收到通知的管理员遭遇重复轰炸。
- 客户端提交内部字段时静默忽略，保持现有设置 API 对未知/不可写字段的兼容行为。

## 测试

### 权限回归

- 构造已通过旧校验、随后被暂停且配置版本仍匹配的用户。
- 调用 `PUT /settings` 提交伪造的健康字段。
- 断言请求不能改变暂停、校验结果、校验时间和错误信息，`share_active` 仍为假。
- 断言普通可写设置仍能在同一请求中保存。

### 系统 AI 告警回归

- 模拟第一次管理员通知写入数为零。
- 断言持久化标志被撤销，后续失败可以再次调用通知。
- 模拟成功写入后，断言后续失败不重复告警。

### 每日摘要告警回归

- 模拟告警抢占成功但管理员通知写入数为零。
- 断言失败记录的 `alerted` 被恢复为 `0`，下一次调用可以重新抢占。
- 成功写入时保持 `alerted = 1`。

## 验收标准

- 权限绕过回归测试先失败、修复后通过。
- 两类告警失败重试测试先失败、修复后通过。
- 完整 pytest 测试套件通过。
- Python 编译、前端内联 JavaScript 语法检查和 `git diff --check` 通过。
