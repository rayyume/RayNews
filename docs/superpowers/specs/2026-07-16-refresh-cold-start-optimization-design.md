# 手动刷新与冷启动优化设计

## 目标

解决以下用户可见问题：

- 右上角手动刷新长时间阻塞，刷新期间又出现“有 X 篇新文章”，导致状态矛盾。
- 左上角 Logo 触发完整抓取，回首页动作不够轻量。
- 容器冷启动时先抓取再启动 Web 服务，偶发连接超时或 502/504。
- 页面冷启动串行等待来源元数据，并强制跳过 IndexedDB 文章缓存，导致分类和文章出现较慢。
- 冷启动网络失败后必须手动刷新才能恢复。

本次不改造固定四分类模型，也不支持动态新增 `MKT` 等一级分类。

## 用户体验

### 手动刷新

右上角“刷新”启动唯一的后台抓取任务并立即返回。按钮在任务运行期间显示“更新中”，但页面可以继续浏览。前端轮询任务状态；任务结束后只请求一次最新第一页并显示：

- `更新完成，新增 N 篇文章`
- `已是最新`
- `更新失败，请稍后重试`

任务运行期间，增量检查可以收集新文章，但不显示独立的“有 X 篇新文章”提示。任务完成后的统一列表更新负责消费这些待显示文章，避免文章已出现但进度条仍运行。

### Logo

Logo 只执行轻量动作：回到全部分类第一页、滚动到顶部，并做一次增量检查。它不再启动完整服务端抓取。

### 冷启动

已有缓存时，页面先显示缓存的来源元数据和文章，再并行向服务器校准。服务器结果回来后复用现有 DOM 差异更新，避免整页二次跳动。

无缓存时，页面显示骨架屏并对短暂网络失败做有限次数自动重试。最终失败时才显示错误操作入口。缓存已经可用时，网络校准失败只显示轻提示，不移除已显示内容。

容器启动时先提供 Nginx/API 服务，再在后台启动首次抓取。已有持久化数据库可以立即读取；全新部署且数据库为空时，页面显示初始化状态，而不是因为 Web 服务尚未监听而超时。

## 架构

### 刷新任务状态

`refresh_server.py` 维护进程内唯一刷新任务状态：

- `job_id`
- `status`: `idle | running | completed | failed`
- `started_at`
- `finished_at`
- `new_count`
- `error`

启动任务时复用现有抓取锁。若已有任务运行，返回同一运行状态而不是启动第二个任务。

接口分为：

- `POST /auth/refresh`：鉴权后启动后台任务，立即返回 `202`；已有任务时返回其状态。
- `GET /auth/refresh/status`：鉴权后返回当前任务状态。

`web_server.py` 只做短请求代理，不再等待 `fetcher.py` 完成。实际抓取仍由 `refresh_server.py` 的工作线程执行。任务开始前后分别获取文章 ID 快照，以稳定计算 `new_count`。

任务状态只包含安全的摘要错误信息，不向普通用户暴露完整抓取日志或服务器路径。

### 前端刷新状态机

前端将“任务运行”和“新文章待显示”合并为一个手动刷新流程：

1. 保存刷新前的最新时间戳或文章 ID 集合。
2. 启动后台任务。
3. 按固定间隔轮询状态；同一页面只能有一个轮询器。
4. 任务运行期间，常规定时 `loadSince()` 不弹提示；结果只进入待显示队列。
5. 任务完成后强制请求一次当前目标页，应用差异、消费相关待显示队列、停止进度动画并显示统一结果。
6. 任务失败或轮询网络失败时保留当前文章，停止动画并显示可重试提示。

轮询有最长等待时间；超时仅表示状态查询失败，不会自动再次提交刷新 POST。

### 冷启动数据流

页面启动后立即执行：

1. 同步渲染固定的一级分类按钮外壳。
2. 从 IndexedDB 读取来源元数据和首页缓存并尽快应用。
3. 并行执行来源元数据、文章第一页、今日文章数和登录校验请求。
4. 网络文章结果到达后使用现有 `reconcileVisibleArticles()` 差异更新。
5. 网络来源元数据到达后重建来源映射、左侧菜单和顶部按钮状态。

缓存不是最终真相；每次启动仍会后台校准。来源配置被管理员修改后，当前管理页面沿用现有刷新依赖视图流程，其他客户端在下次启动、前台恢复或增量检查时获取最新元数据。

### 容器启动顺序

`entrypoint.sh` 不再在启动服务之前同步运行 `fetcher.py`。`refresh_server.py` 在 HTTP 服务开始监听后，用后台线程触发一次启动抓取，并继续保留周期抓取。

启动抓取与手动/周期抓取共享同一把锁，避免服务刚启动时产生重复抓取任务。

## 超时与错误处理

- 异步刷新启动和状态接口都是短请求，不依赖 120/150 秒长连接。
- Nginx `/auth/` 设置明确且一致的连接、发送和读取超时，避免使用不透明默认值。
- 冷启动文章网络请求保留边界超时，但有缓存时不进入阻塞错误页。
- 无缓存时按短退避自动重试有限次数；重试耗尽后显示明确错误。
- 刷新失败不会清空文章、缓存或待显示内容。
- 页面离开、重新进入后台或启动新导航时，旧轮询器和旧请求必须可取消或失效。

## 性能边界

本次优先优化等待模型和首屏路径，不改变 Telegram/Telegraph 正文抓取算法。实际抓取总时长仍受外部源站影响，但用户不再被同步 HTTP 请求阻塞。

来源元数据请求不再阻塞文章请求。若部署数据量下 `/sources` 仍明显缓慢，后续可将来源维护与读取拆分，并增加服务端修订号/ETag；这不作为本次正确性修复的前置条件。

## 测试

### 后端

- 启动刷新任务立即返回，不等待抓取器结束。
- 同时提交多个刷新请求只运行一个任务。
- 状态从 `running` 正确转为 `completed` 或 `failed`。
- `new_count` 使用任务前后文章 ID 差集计算。
- 状态接口要求登录，且不泄露完整内部日志。
- 启动后台抓取和周期抓取复用同一锁。

### 前端契约

- Logo 不调用完整刷新接口，只回首页并增量检查。
- 手动刷新只提交一次 POST，之后轮询状态。
- 手动刷新运行期间不显示独立新文章提示。
- 完成后只进行一次权威列表校准并停止动画。
- 冷启动允许使用文章缓存，来源与文章请求不再串行。
- 顶部一级分类按钮在来源网络请求完成前即可渲染。
- 有缓存的网络超时保留已显示文章。

### 启动与回归

- 静态验证 `entrypoint.sh` 在同步抓取前启动服务，或完全移除同步启动抓取。
- 使用临时数据库和模拟抓取器做接口级验证。
- 运行完整 `pytest` 测试集。
- 若本地可启动完整应用，再验证桌面和移动视口的冷启动、刷新、重复点击和失败恢复；没有生产地址时明确记录未覆盖的真实源站耗时。

## 非目标

- 动态创建一级分类。
- 修改 AI 翻译、摘要或图片缓存策略。
- 重写抓取器或改变 Telegram 历史抓取范围。
- 引入跨进程持久化任务队列。
